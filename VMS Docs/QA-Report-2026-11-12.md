# VMS QA and system audit report

**Run ID:** QA-1112   **Date:** 12 November 2026 (Asia/Manila)   **Environment:** local development (API http://127.0.0.1:8001, SPA http://localhost:5173, MySQL `barangay_vms_db`)
**Revision:** branch `dev-paul` at commit bd667bc plus later uncommitted UI changes (table row height, dropdown width, Condition Check layout, Readiness Check move). Deployed revision: not applicable (local).
**Browser:** Chromium 1228 driven by Playwright, viewports 1366x900 and 450x900. API checks sent directly with each role's session token.
**Audience:** developers and barangay representatives.

## 1. Outcome in plain language

I ran **298 cases**: **291 pass, 5 fail, 2 blocked/not a product failure.** The ticket workflow, the new Return to Admin feature, the external-shop tester, retired-only cannibalization donors, role permissions and barangay isolation behaved as intended in every executed case, with one important exception.

**Release blocker found (QA-001, High, P1):** when a repair proposal is declined, cancelled or deleted, the vehicle stays marked **Needs Repair** and its linked issue report goes back to **Pending**. A new Good condition check is saved but does not clear it, and the readiness check is refused. Nothing in the normal screens can clear it: only an Admin opening a direct link (`/admin/issues/<id>`) or the API can dismiss the hidden report. The decline notice I added earlier today ("the vehicle stays Needs Repair until a new Condition Check") is therefore inaccurate and should be corrected or the defect fixed.

Five lower-priority findings and one environment note follow. This is finite browser testing: it does not certify that no other defects or security weaknesses exist. See section 7 for what was not tested.

## 3. Finding details

### QA-001 - A declined, cancelled or deleted proposal leaves the vehicle stuck on Needs Repair

- **Classification:** workflow/role conflict and data integrity; High (a core workflow, readiness, is blocked and the only workaround is not discoverable); P1; Confirmed.
- **Location/actors:** Custodian A, Admin A, vehicles QA-1112 Truck 3, 7 and 8 (synthetic).
- **Expected:** a Declined proposal "does not certify the defect is repaired", and the Custodian can run a new Condition Check to correct the vehicle (rule stated in the decline notice added on 12 November). After a mistaken proposal is deleted the vehicle should not stay flagged.
- **Reproduction (realistic path):**
  1. Custodian records a Condition Check with result Needs Repair (vehicle becomes Under Maintenance / Needs Repair; issue report Under Review is created).
  2. Custodian proposes a repair linked to that check.
  3. Admin declines it with a reason (the same happens when an untouched proposal is deleted).
  4. Custodian records a new Condition Check with result Good (HTTP 201).
  5. Open the vehicle list and try the Readiness Check.
- **Actual:** after step 3 the vehicle is Available / Needs Repair and the issue report is Pending. After step 4 the vehicle is still Available / Needs Repair, readiness state "in maintenance", and the readiness check returns 422 "Resolve the open repair proposal or issue first". Issue Reports have no sidebar entry for any role; an Admin who knows the link `/admin/issues/<id>` sees a Dismiss button, and `PUT /issues/{id}/dismiss` clears the state (vehicle becomes Good, readiness check accepted). Cancel was not repeated as a separate case; it uses the same report reset, so it is likely affected (unverified).
- **Evidence:** ledger STUCK-01 to STUCK-04 (HTTP statuses and vehicle states above). No screenshots; API and browser observation.
- **Impact:** any declined proposal can permanently remove a vehicle from the Ready list until someone with the hidden link or API access dismisses a report the Custodian cannot see.
- **Cause:** hypothesis from the observed states: decline, cancel and delete reset the linked issue report to Pending, and the readiness rule treats a Pending report as an open problem; a Good condition check does not resolve Pending reports. Next diagnostic step: read the readiness-block rule and the decline/cancel/delete handlers together.
- **Proposed solution (smallest first):** (a) when a proposal is declined, cancelled or deleted and its source report was created for that proposal, dismiss the report automatically with the reason "proposal withdrawn" and recompute the vehicle's condition; (b) alternatively let a Custodian's Good Condition Check resolve pending reports on that vehicle, with a confirmation; (c) until fixed, change the decline notice so it does not promise a Condition Check will clear it. Tradeoff: (a) is automatic but could hide a genuine unresolved fault if the Admin declined for another reason; (b) keeps the Custodian in control.
- **Acceptance:** after decline, cancel or delete, the Custodian can reach a Ready vehicle through a visible, documented path; no vehicle remains Needs Repair with only a hidden Pending report; wrong roles still cannot dismiss.
- **Regression:** the original case, a decline followed by Admin reconsider and approval, a vehicle with two proposals, cancel and restore, and the Needs Repair condition check path.
- **Workaround:** Admin opens `/admin/issues/<id>` and uses Dismiss (or the API). Not discoverable.

### QA-002 - The account switcher can impersonate the Super Admin account

- **Classification:** requirements discrepancy; Low; P3; Confirmed; Needs policy decision.
- **Expected:** the supplied baseline says Super Admin accounts are not impersonation targets. **Actual:** the dedicated switcher account is listed with the Super Admin account as a candidate and `POST /impersonate/1` returns HTTP 200 with a Super Admin session. The rule in code only blocks a Super Admin impersonating another Super Admin. The switcher is a development convenience here; I did not see whether it exists in a deployed build.
- **Proposed solution:** decide whether the switcher may enter Super Admin. If not, remove it from the candidate list and refuse it on the server. **Acceptance:** the Super Admin id is absent from candidates and the request returns 403.

### QA-003 - A maintenance schedule dated in the past is accepted

- **Classification:** functional bug (validation) or policy gap; Low; P2; Confirmed; Needs policy decision.
- **Actual:** `POST /maintenance-schedules` with a date three days ago returned 201. The server rule for the date is only "required, date". The schedule is born overdue and would be auto-proposed as a ticket as soon as the due-job runs (job not executed in this audit).
- **Proposed solution:** reject dates before today for new bookings, or allow them only with an explicit "record a missed service" option. **Acceptance:** past date returns 422 with a clear message; today and future dates still save.

### QA-004 - Record Repair Work does not preselect the repair method

- **Classification:** UX; Low; P3; Confirmed.
- **Actual:** for a ticket proposed and approved as Cannibalized, the page opens with neither Standard Repair nor Uses Parts From Another Vehicle selected; the mechanic must re-choose. The code comment says this is deliberate ("personnel explicitly choose the method each visit"). The donor named in the proposal is only visible after choosing the method.
- **Proposed solution:** preselect the proposed method (still changeable) and show the proposed donor. **Acceptance:** a cannibalized proposal opens with that method selected and the donor listed.

### QA-005 - Evidence links are bearer URLs for a few minutes

- **Classification:** security/authorization (informational, historical lead "file signing"); P3; Confirmed; Needs policy decision.
- **Actual:** a repair-evidence file link with a valid signature opened with no login and with an other-barangay token (HTTP 200). The same URL with the signature removed or altered returned 403 for everyone, including the owner's own session. The link was valid for about 6 minutes when minted.
- **Impact:** anyone who receives a freshly minted link (for example from a copied URL or log) can open the file until it expires. This is a common design, not a bypass.
- **Proposed solution:** accept it as designed, or bind links to the session or shorten the lifetime. **Acceptance:** the documented policy matches the behaviour.

### QA-006 - Notifications about a deleted ticket remain with no link

- **Classification:** UX; Low; P3; Confirmed. Four notices ("Ticket #13 is back under Admin review", and similar) stayed after their tickets were deleted, with an empty ticket link. **Proposed solution:** remove or mark as resolved the notices of a deleted ticket. **Acceptance:** none remain.

### QA-007 - Impersonation rate limit (environment)

- **Classification:** environment limitation. Impersonation allows 10 requests per minute; two quick runs exhausted it and some role sessions were never issued, which produced false failures in my first run of part 2 (discarded; the run was repeated with spacing). Not a product defect.
